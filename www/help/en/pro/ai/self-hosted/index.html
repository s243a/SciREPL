Use your own AI server

Connect Pro to an Ollama server or another compatible chat-completions endpoint that you control. Configure its provider in AI Settings, then test with one no-tools AI Prompt cell before trying the Assistant's workbook tools.

  • Pro only
  • Current Pro 1.5.0 controls
  • English-first guide

This new guide is currently English only. It is separate from the existing translated tutorial set. It describes current endpoint controls, not a promise that every server, model or network configuration has been tested.

Three different things: a self-hosted model is a Direct AI provider; Android's on-device completion model is a separate feature; Remote bridge connects an external coding agent through an MCP broker. This lesson does not require Remote, an SSH session or a coding agent.

Here the computer runs the model and the phone is the client. You do not need to install an Ollama server or download a model onto Android for this setup. Pro's optional Android on-device completion model is not that server.

1. Check the server on its own computer

Install Ollama using its official setup instructions. Choose a local model that fits that computer's memory; downloads can be large. This guide does not require an Ollama cloud model or a paid cloud API key.

Command examples use a Linux/macOS shell. WSL and Windows can have different loopback network namespaces: WSL's 127.0.0.1 is not automatically the Windows Ollama app's 127.0.0.1. Run the gateway and Ollama in the same host OS/network namespace, or arrange explicit, approved local forwarding. Native Windows uses different quoting and environment-variable syntax; follow Ollama's Windows instructions when configuring its Windows app.

On the server computer, list the models you have installed:

ollama list

Keep the exact model name, including its tag. If needed, deliberately download a model with ollama pull MODEL_NAME, replacing MODEL_NAME with your choice. If the server is not running, start it with ollama serve; do not start a second copy over an existing desktop app or service.

Verify a small request there first. Replace MODEL_NAME below with the installed name:

curl http://127.0.0.1:11434/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"MODEL_NAME","messages":[{"role":"user","content":"Say hello in one sentence."}],"stream":false}'

The response should contain choices[0].message.content. This uses Ollama's OpenAI-compatible chat-completions API, not its native /api/chat API. Terminal success proves server/model readiness, not phone connectivity or browser CORS.

2. Reach it securely from SciREPL

Localhost means the device running SciREPL. On a phone it is the phone, not your PC. Use the computer's private HTTPS hostname when the model runs elsewhere.

Server locationFull API Endpoint
Same device, reachable on loopbackhttp://127.0.0.1:11434/v1/chat/completions
Another computer through a private TLS proxyhttps://YOUR_HOST:8443/v1/chat/completions

HTTPS is required for a non-loopback host. Plain LAN HTTP, such as http://192.168.1.20:11434/…, and plain HTTP to a Tailscale IP are rejected by the current endpoint policy. A private network does not bypass it. The device must trust the certificate and its hostname must match; do not disable certificate checks.

Prepare a loopback gateway before Tailscale Serve

Do not point Serve directly at Ollama. Serve preserves the public-facing Host header, which a loopback-bound Ollama server can reject. OLLAMA_ORIGINS controls CORS, not this Host check. Put a trusted, reviewed gateway at 127.0.0.1:11435 in front of Ollama at 127.0.0.1:11434.

The gateway must check its own Bearer token, allow only your intended app origins, answer their CORS preflights, and normalize the upstream Host to localhost:11434. Your app uses the gateway's credential. The following NGINX fragment illustrates only the loopback/upstream routing and Host rewrite, following Ollama's proxy example and the NGINX header reference:

server {
    listen 127.0.0.1:11435;
    location = /v1/chat/completions {
        proxy_pass http://127.0.0.1:11434;
        proxy_set_header Host localhost:11434;
    }
}

This fragment is not a complete secure gateway. It omits Bearer-token authentication and CORS/preflight policy. Use an existing gateway with those controls, or have its administrator complete and review the configuration before sharing it. Do not deploy this routing fragment alone, accept every origin, or expose Ollama's listener to the network to get around a 403.

Verify that the gateway rejects a missing/wrong token, accepts your intended app origin and the Authorization/Content-Type headers, and successfully proxies one small authenticated chat request. The gateway and Ollama must be reachable from the same host OS/network namespace. Only then enable the private HTTPS mapping below.

Share the prepared gateway privately

  1. Put the server computer and phone on your authorized Tailscale network. Restrict which devices/users can reach the service. Enable tailnet HTTPS certificate support when prompted.
  2. Keep Ollama on 127.0.0.1:11434 and the prepared gateway on 127.0.0.1:11435. Check existing mappings first with tailscale serve status.
  3. If HTTPS port 8443 is unused in that configuration, run this on the server computer. It changes Serve configuration; do not overwrite an existing mapping:
tailscale serve --https=8443 http://127.0.0.1:11435

Copy the exact HTTPS hostname and port printed by Serve, then append /v1/chat/completions. Keep this foreground command running while testing; stop this session with Ctrl+C when done. Use Serve, not Funnel: private tailnet access is the goal, not a public model server. Check the current Serve command reference and access and HTTPS requirements.

Allow the app's web origin, not every website

The gateway must permit the app's actual Origin through CORS, including preflight requests for JSON and the Authorization header. Android Pro normally uses https://localhost; a browser preview uses its page's own origin. Origin is not the model server's hostname. A preflight must be handled without requiring the Bearer token on the OPTIONS request; the actual POST still requires authentication. Check request/log information rather than guessing.

Ollama supports OLLAMA_ORIGINS. For example, a manually managed server for Android Pro can be started with:

OLLAMA_HOST=127.0.0.1:11434 OLLAMA_ORIGINS=https://localhost ollama serve

Use this instead of another running Ollama instance, not alongside it. It may be needed when the gateway forwards the validated app origin upstream; it does not replace gateway authentication or fix a wrong Host header. For the Windows/macOS app or a Linux service, follow Ollama's platform-specific environment/restart instructions and origin guidance. Allow only the origins you need. CORS is not authentication; tailnet access controls and the authenticated gateway still matter.

Related SciREPL networking instructions: the public SciREPL-MCP Tailscale guide and broker setup guide explain private Serve access. Reuse the transport concepts, not their broker URLs: wss://HOST/app and https://HOST/mcp are MCP routes. Neither is a Direct AI model endpoint.

3. Set up Pro's AI Assistant

  1. Open Menu → AI Assistant (Pro), then the panel's ⚙ gear → AI Settings.
  2. Set Configure model for → AI Assistant, then Backend → Ollama (local). Keep Remote bridge off for this Direct AI setup.
  3. In Model, use Or enter custom model ID for the exact installed ID if it is not listed.
  4. Set API Endpoint to the complete chat URL, including /v1/chat/completions. SciREPL does not append that suffix. A hostname or /v1 alone is insufficient.
  5. Set API Key for this provider/endpoint pair. Current Pro requires a nonempty saved key even for a keyless local Ollama server. For a standard local server that ignores it, use the non-secret placeholder ollama. If your server/proxy authenticates requests, use its real key instead. Do not send a paid cloud-provider key to an unrelated server.
  6. Tap Save. Saving does not make a model request. A key saved for a different endpoint is not automatically reused. Current AI Prompt requests follow this Assistant provider, model, endpoint and key.

Protect saved keys. They are stored locally without application-level encryption and the matching key is sent to the selected endpoint. Keep secrets out of cells, screenshots and exports; read the Pro privacy policy.

Another OpenAI-compatible server

The configurable Ollama (local) backend can also target a trusted server implementing the compatible chat-completions request/response format. Use its full HTTPS chat URL, exact model ID and authentication. The label does not guarantee every server works. The OpenAI backend uses its fixed provider endpoint; it is not the custom-server choice. Start with the no-tools AI Prompt test below: tools, reasoning options and streaming support vary.

4. Test with a no-tools AI Prompt cell

  1. Create an empty practice workbook, with no private code, files or conversation. Keep the cell type Code and choose AI Prompt in the language/mode dropdown. If absent, enable it under Menu → Languages & modes. Do not put this test in the Assistant's message box.
  2. Enter Reply with the digit 2 only. Open the cell's Configure control. Set Put final response in → This cell’s output (default) and Context to send → Include source from → No other cells (default). Tap Save configuration.
  3. Press Run. Read the Direct AI disclosure before accepting it. If a request-context review appears, confirm that no other cells are selected. Declining cancels the send. This sends one isolated prompt plus fixed system guidance, without Assistant history, automatic every-cell previews or tools. Your chosen server and proxy can receive or log it; self-hosted does not mean data stays on the phone.
  4. Check for 2 in this cell's output. This validates one small text request, not every model feature. It does not execute generated code or create a workbook-tool grant.

Current provider behavior: AI Prompt cells use Follow AI Assistant. The Independent provider and model (preview) settings are not the active request path yet. For now, change the Assistant's provider/model/endpoint when you want to change this Prompt test's destination. See the existing AI Prompt cell walkthrough for the configuration controls.

The Assistant is a later, different test. Its requests advertise workbook tools even when Review is selected. Use a model/server that supports compatible tool calling, then review tool permissions before attempting workbook tasks. Review does not turn the Assistant into a no-tools chat endpoint; do not grant standing execution or file access merely to test connectivity.

Troubleshooting in order

  • Terminal request fails: fix server availability, installed model ID, memory or authentication on the server first.
  • Phone cannot reach the host: check both devices, tailnet access rules, Serve port and hostname/certificate trust. A model on your PC is not at the phone's localhost.
  • Endpoint rejected: use HTTPS for a remote host and a complete URL. Do not bypass the policy with an insecure LAN URL.
  • CORS/preflight error: allow the exact app origin and required headers at the server/proxy. Terminal success alone does not test CORS.
  • No API key configured or HTTP 401/403: save the gateway's key for this exact provider/endpoint; a dummy is only for a genuinely keyless direct server. Check the gateway's token/access policy and the upstream Host rewrite. Changing CORS origins alone does not fix Ollama's Host rejection.
  • AI Prompt works but Assistant fails: check tool-calling support. A successful no-tools Prompt does not prove that the model accepts Assistant tool definitions.
  • 404, model missing or unsupported parameters: check the chat path, model ID and compatibility. Native Ollama API URLs are not chat-completions endpoints.

This English-first guide can grow with verified app support. It does not claim a built-in server installer, automatic LAN discovery, universal model/tool compatibility or automatic SSH/MCP setup.
